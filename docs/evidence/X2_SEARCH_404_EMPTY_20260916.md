## 1. Ownership boundary

X2 hardens the Theme presentation for native WordPress Search, 404 and empty Archive states only.

WordPress remains authoritative for:
- search query semantics and the main query;
- archive state;
- 404 routing and HTTP status;
- native search-form submission semantics;
- content and URLs.

AZnet Theme owns only:
- Search/404/empty-state markup composition inside Theme templates;
- recovery hierarchy and actions;
- responsive/focus presentation;
- the surface-scoped `recovery.css` asset gate.

X2 does **not** add a custom query/ranking engine, redirect heuristics, private storage reads, SEO metadata/schema ownership, provider behavior or a generic form framework. Theme metadata remains `1.1.0`.

## 6. Debugging record

Three failures were reduced to test-harness root causes before closure:

1. **`wp eval-file` + `strict_types`:** the first runtime fixture used `declare(strict_types=1)`, which is invalid after WP-CLI wraps/evaluates the file. Existing repository `wp eval-file` fixtures use no such declaration. The declaration was removed from the fixture only; production code was unchanged.
2. **Pretty-path 404 under PHP built-in server:** `/x2-definitely-not-a-real-route/` was handled by the disposable PHP server as Home/200 rather than WordPress 404. The fixture was changed to the native missing-Post query `?p=999999999`, which exercises WordPress 404 truth without changing production routing.
3. **Expected 404 console signal:** Chromium logs a console error for an expected main-document HTTP 404. The browser harness now distinguishes that expected navigation response from unexpected 4xx/5xx resources, other console errors and page errors. Unexpected browser failures remain hard failures.

An earlier run `35070924185` therefore remains diagnostic evidence, not PASS evidence: 12/16 cases passed and the four 404 cases already had correct HTTP 404, H1, zero overflow and zero blocking Axe findings, but were intentionally rejected by the then-overbroad console-error assertion.
