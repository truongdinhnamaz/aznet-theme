# AZnet Theme v1.2 — WordPress Experience Completion Design

**Status:** Owner-approved design / source-ratification artifact
**Date:** 16/09/2026  
**Repository:** `truongdinhnamaz/aznet-theme`  
**Base:** `main@31a05ebb3701b8941e31da1a336dae304d44f31a`  
**Product scope:** AZnet Theme only

## 1. Purpose

v1.2 completes the native WordPress user experience of AZnet Theme after the v1.1 release-critical path reached publication and production deployment PASS.

The milestone intentionally stays inside Theme ownership. It improves presentation, composition, responsive behavior and accessibility of WordPress Core surfaces. It does not open a new provider/plugin integration program and does not transfer WordPress or external-domain semantics into the Theme.

The product-owner-approved direction is:

- complete the broad WordPress Core surface set to production-ready quality;
- deeply polish three priority surfaces: Comments; Search/404/empty states; Media/gallery/embed;
- keep pagination/navigation and native form controls production-ready without turning them into large subsystems;
- use surface modules over a monolithic Core Experience layer;
- retain shared primitives and the existing hybrid PHP + `theme.json` architecture;
- keep Theme metadata at `1.1.0` during implementation and promote atomically to `1.2.0` only at final release closure.

## 2. Product and ownership boundary

The governing rule remains:

> SOURCE OWNS DATA. THEME OWNS PRESENTATION. INTEGRATION CONTRACTS CONNECT THEM.

### WordPress owns

- comment data, moderation, threading, reply state and comment lifecycle;
- search query semantics and the WordPress main query;
- 404 routing;
- Post/Page/media content state;
- gallery/embed/native block semantics;
- pagination state and native navigation semantics;
- form submission and validation semantics owned by WordPress Core.

### Theme owns

- markup composition inside Theme templates where WordPress expects Theme markup;
- spacing, typography, surfaces, borders and responsive layout;
- presentation of focus, keyboard-visible states and accessible visual hierarchy;
- generic empty/error/recovery presentation;
- surface-aware loading of Theme-owned assets;
- editor/frontend visual parity where `theme.json` is the correct layer.

### Explicitly outside v1.2

- RootProfile, ConvertFlow, WooCommerce or other provider certification work;
- provider public-contract changes;
- private provider APIs/storage, authoritative routing heuristics or copied domain logic;
- custom search/ranking engine;
- custom comment engine or comment datastore;
- custom gallery/lightbox application engine unless separately ratified by a future source decision;
- page builder, FSE takeover, mega-framework or new build stack;
- SEO canonical/meta/schema/OG ownership;
- legal/business-domain semantics.

AZT-05 v1.0 remains unchanged. This milestone is compatible with the existing product constitution.

## 3. Architectural choice

### Selected approach: Surface modules + shared primitives

The existing shared presentation layer remains the base. In particular, existing content shell, listing/card primitives, basic pagination and empty-state presentation are extended rather than replaced.

New behavior is split by surface responsibility instead of collected into one monolithic `core-experience` subsystem.

Expected module shape, subject to implementation-plan validation:

- `comments` surface module;
- `media/content` presentation module;
- shared native form primitives;
- bounded refinements to existing generic search/404/empty/navigation presentation.

A module is introduced only when the surface has distinct markup or asset needs. Shared tokens and primitives remain shared. Surface-specific assets should not be globally loaded when reliable WordPress-native surface detection can keep them bounded.

### Rejected alternatives

**One large Core Experience layer:** fewer files initially, but it would mix unrelated responsibilities and encourage unnecessary global loading.

**Theme.json-first for every surface:** useful for editor/frontend parity on block/content styling, but comments/search/404 are still PHP-template surfaces. Forcing them into `theme.json` would obscure the existing hybrid boundary.

## 4. Data flow and fail-soft model

The default data flow is:

`WordPress native API/state -> Theme template/helper -> Theme presentation`

The Theme does not create a parallel source of truth.

Fail-soft rules:

- missing comments do not create fake comment data or substitute provider content;
- empty search results render a useful recovery state while preserving WordPress query truth;
- 404 remains WordPress routing truth and receives Theme-owned recovery presentation only;
- absent or malformed media/embed output must not break layout or create unsafe inference;
- forms keep WordPress-owned action/submission semantics;
- no fallback may direct-read plugin-private option/meta/CPT/table/class storage.

## 5. v1.2 execution slices

### X1 — Comments Surface

**Goal:** add a complete native WordPress comments presentation surface.

**Expected WordPress APIs:** `comments_template()`, `wp_list_comments()`, `comment_form()` and native comment pagination/reply behavior as appropriate.

**Theme responsibilities:** hierarchy, spacing, typography, avatar presentation, metadata presentation, nested-thread readability, reply links, focus states, responsive behavior.

**Forbidden:** custom comment persistence/moderation/reply engine, copied WordPress comment lifecycle, provider identity takeover.

**Priority:** deep polish surface #1.

### X2 — Search / 404 / Empty States

**Goal:** turn existing minimal native fallbacks into clear recovery and discovery experiences without taking over query/routing semantics.

**Theme responsibilities:** headings, layout, search form presentation, result/empty hierarchy, recovery actions, focus states, responsive behavior.

**Forbidden:** custom search ranking/query engine, authoritative redirects inferred from slug/title/Page ID/URL heuristics.

**Priority:** deep polish surface #2.

### X3 — Media / Gallery / Embed

**Goal:** make native editorial media robust across long-form content and common WordPress media/block output.

**Coverage:** images, figures/captions, galleries, video/audio, iframe/embed, alignment, wide content, overflow and responsive behavior.

Use `theme.json` where it genuinely improves editor/frontend parity; use bounded PHP/CSS presentation where template/content surfaces require it.

**Forbidden:** new gallery domain store, lightbox application engine or media workflow takeover.

**Priority:** deep polish surface #3.

### X4 — Pagination & Navigation Completion

**Goal:** production-ready presentation for archive/search pagination, Post page links, previous/next navigation and comment pagination where applicable.

WordPress remains authoritative for pagination/navigation state and URLs.

Do not create a separate navigation application framework.

### X5 — Native Form Controls

**Goal:** consistent production-ready presentation for WordPress-native controls used by search, comments and generic native Theme surfaces.

**Coverage:** input, select, textarea, button, labels, focus-visible, disabled and error/notice presentation where the Theme legitimately controls it.

Shared primitives come before surface overrides.

**Forbidden:** private plugin selectors/contracts or a generic plugin-form skinning engine.

### X6 — Cross-surface QA & Release Closure

**Goal:** close v1.2 only after the implemented WordPress Core surfaces pass the existing release discipline.

Minimum closure:

- L1 static/naming/private-storage/dependency scans;
- L2 RED -> intended failure -> minimal GREEN -> retained regression for production feature behavior;
- L3 real WordPress runtime;
- L4 browser/responsive/keyboard/focus/landmark/overflow/a11y at representative desktop/tablet/mobile viewports, including editor/frontend parity where applicable;
- L6 deterministic package, package/source identity, update/theme-switch continuity, rollback and exact-main verification before promotion.

Provider L5 is outside this milestone and must not be inferred from v1.2 Core PASS.

## 6. Execution order

Approved sequence:

`X1 Comments -> X2 Search/404 -> X3 Media -> X4 Navigation -> X5 Forms -> X6 Closure`

Rationale:

- Comments is the clearest native Core surface gap and therefore comes first.
- Search/404 already has a baseline template, making it a contained hardening slice after Comments.
- Media work can then build on the established content/form/focus primitives without forcing a premature broad abstraction.
- Navigation and form completion follow once the three deep-polish surfaces reveal what shared primitives are actually needed.
- X6 closes only final verified bytes.

## 7. Acceptance discipline per slice

Each X1-X5 slice must define:

- one bounded goal;
- owner and dependency boundary;
- allowed APIs/files;
- forbidden scope;
- RED evidence that fails for the intended pre-change reason;
- minimal GREEN implementation;
- related regression evidence;
- L3 runtime evidence;
- L4 responsive/accessibility evidence;
- surface-aware asset expectation;
- rollback/recovery checkpoint;
- exactly one Next.

No PASS may be inferred between QA layers.

A deeper failure must be reduced to the shallowest stable reproduction before production code is changed.

## 8. Versioning and release behavior

The implementation program is referred to as **v1.2**, but Theme runtime metadata remains `1.1.0` while X1-X5 are under development.

Promotion to exact `1.2.0` occurs only in X6 and only after fresh evidence on the final candidate bytes. Version metadata must be promoted atomically across all Theme-owned version declarations.

Publication and production deployment remain separate owner gates after technical release closure, consistent with existing governance.

## 10. Recovery and rollback

Every implementation slice is bounded and independently reversible.

- New comments/template presentation can be reverted without deleting WordPress comments.
- Search/404 presentation rollback must not alter WordPress routing/query state.
- Media styling rollback must leave WordPress media/content untouched.
- Form/pagination presentation rollback must leave native WordPress state untouched.
- Theme switching must continue to preserve WordPress-owned content and all external domain data.
