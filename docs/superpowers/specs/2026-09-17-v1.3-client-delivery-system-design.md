# AZnet Theme v1.3 — Client Delivery System Design

**Status:** Design approved in chat; written-spec review pending  
**Date:** 17/09/2026  
**Canonical base:** `main@5d10bdcf583b020a589c713a33a5a15f377ba3dc`  
**Target product:** AZnet Theme only

## 1. Purpose

AZnet Theme v1.3 is the **Client Delivery System** milestone.

The milestone optimizes the Theme for a practical delivery outcome: AZnet should be able to take a clean WordPress site from installation to a visually coherent, professional, client-ready service/business website materially faster than with v1.2, without turning the Theme into a page builder or domain engine.

v1.3 focuses on the gap that remains after v1.2 WordPress Experience Completion: the Theme already has strong core templates, Homepage composition, patterns, Header, Woo presentation, comments/search/media/navigation/forms, release infrastructure and a production-verified standalone core, but native inner Pages and general client handoff composition remain less productized than the rest of the system.

## 2. Governing principles

The existing architecture remains authoritative:

- **SOURCE OWNS DATA. THEME OWNS PRESENTATION. INTEGRATION CONTRACTS CONNECT THEM.**
- WordPress owns Page/Post/Menu/Media/query state and native lifecycle semantics.
- AZnet Theme owns site-shell presentation, layout primitives, visual composition, responsive/accessibility behavior and bounded presentation settings.
- RootProfile, ConvertFlow and WooCommerce retain their existing domain ownership.
- No private provider API/storage reads, URL/title/slug/Page-ID authority heuristics or parallel domain stores are introduced.
- WordPress + Theme alone must remain a complete Standalone Core path.
- Existing `aznet_theme_settings` remains the single Theme-owned settings schema; v1.3 creates no second Theme settings store.
- Native WordPress content and patterns remain portable; v1.3 creates no proprietary serialized page format.

## 3. Product outcome

A successful v1.3 release must make the following workflow practical:

1. Install/activate AZnet Theme on clean WordPress.
2. Run a visible, confirmed professional-services setup plan or configure an existing site manually.
3. Obtain a coherent Homepage + About + Services + Team/Expertise + Contact + Blog/navigation structure using WordPress-native content.
4. Apply production-quality inner Page presentation and Footer presentation without copying domain truth into the Theme.
5. Replace placeholder/editorial copy with client-owned content directly in WordPress.
6. Verify desktop/tablet/mobile, keyboard/focus, accessibility, update/theme-switch continuity and deterministic package identity.
7. Hand the site to the client without requiring a proprietary builder or optional ecosystem plugin for core operation.

The milestone is judged by this end-to-end delivery outcome, not by feature count.

## 4. Scope

v1.3 is split into five bounded slices:

- **Y1 — Page Experience 2.0**
- **Y2 — Professional Page Kits**
- **Y3 — Footer System 2.0**
- **Y4 — Professional Services Starter Blueprint**
- **Y5 — Client Delivery QA & Release Closure**

Execution order is `Y1 -> Y2 -> Y3 -> Y4 -> Y5` unless fresh evidence proves a dependency requires a small reordering. A slice cannot claim a deeper QA layer from shallower evidence.

## 5. Y1 — Page Experience 2.0

### 5.1 Goal

Raise native WordPress Page presentation to the quality already established on Homepage and editorial Post surfaces while remaining safe for existing content.

### 5.2 Data ownership

Y1 may consume only WordPress-native Page facts:

- Page title;
- excerpt when explicitly authored;
- featured image;
- parent/ancestor hierarchy;
- body content through the normal `the_content()` boundary;
- native Page template selection.

The Theme may style and compose these facts but does not reinterpret them as business semantics or SEO truth.

### 5.3 Default Page surface

The default Page remains compatible with normal WordPress content and retains exactly one document-level Theme `<main>`.

Its presentation becomes:

- a bounded Page header/hero;
- H1 from the WordPress Page title;
- optional authored excerpt as supporting text;
- optional featured image presentation;
- optional breadcrumb navigation only when the Page has a real WordPress ancestor chain;
- content shell and long-form block typography consistent with the Theme design system;
- `wp_link_pages()` retained for native multipage Page content.

No breadcrumb schema is emitted. Y1 is visual/navigation presentation only.

### 5.4 Breadcrumb rule

Breadcrumbs are derived only from WordPress-native hierarchy using the current Page and its real ancestors. They are not generated from URL parsing, slug inference, menu position, Page title matching or plugin state.

To reduce unnecessary duplication, the default Theme breadcrumb is shown only for hierarchical child Pages. Top-level Pages do not receive a breadcrumb by default.

A bounded Theme-owned setting may disable Theme breadcrumbs globally. It must use the existing versioned `aznet_theme_settings` schema.

### 5.5 Layout variants

v1.3 supports three bounded Page presentation variants:

- **Standard** — normal Page header + constrained reading/content width.
- **Wide** — normal Page header + wider WordPress content canvas for block-heavy service/about pages.
- **Landing** — reduced Theme chrome around the Page content while retaining Header/Footer and accessibility landmarks; intended for WordPress-authored campaign/service compositions, not conversion-state ownership.

Per-Page selection uses WordPress-native Page Template state where a per-Page choice is required. No custom Page-layout meta store is introduced.

Shared rendering primitives should prevent three independent copies of Page logic.

### 5.6 Backward compatibility

Y1 must not require content migration. Existing `the_content()` content, featured images, parent relationships and Page template state remain authoritative.

Update from v1.2 must preserve current WordPress Page data and Theme settings. If optional new settings are absent, safe defaults are used.

## 6. Y2 — Professional Page Kits

### 6.1 Goal

Provide reusable, editable native compositions for the most common client-delivery pages without adding a page builder.

### 6.2 Kits

Y2 provides curated full-page or section-pattern compositions for:

1. **About / Giới thiệu**
2. **Services / Dịch vụ**
3. **Team / Expertise / Đội ngũ**
4. **Contact / Liên hệ**
5. **Content Landing / Trang nội dung chuyên đề**

The exact visible wording can be localized, but the patterns remain generic and must not embed law-specific, medical, commerce or other vertical-domain claims.

### 6.3 Pattern architecture

Y2 reuses existing native pattern primitives where possible instead of creating near-duplicates. Full-page kits may compose existing hero, trust, alternating-content, FAQ, CTA and article-grid primitives plus a small number of new generic primitives only when a real gap exists.

Inserted content becomes normal WordPress block content. After insertion, WordPress owns it. Theme switching must not destroy the authored Page content.

### 6.4 Placeholder discipline

Patterns may contain clearly replaceable sample/editorial placeholder copy, but must not invent authoritative client facts such as:

- named people;
- addresses;
- phone/email identities;
- years of experience;
- certifications;
- customer counts;
- guarantees;
- service claims represented as factual business truth.

The Theme does not silently convert site title/tagline or inferred URLs into business claims.

## 7. Y3 — Footer System 2.0

### 7.1 Goal

Turn the Footer into a deliberately finished client-delivery surface instead of a single fixed composition.

### 7.2 Existing truth sources retained

Footer data continues to come from:

- WordPress site title/tagline/custom logo;
- existing WordPress menu locations for navigation, contact, social and policy links;
- optional public provider projection only where an already accepted public contract explicitly supports it.

v1.3 does not create a Footer contact/social database.

### 7.3 Bounded presets

Y3 provides three curated presets:

- **Standard** — current balanced brand/navigation/contact + lower social/policy composition.
- **Professional** — stronger multi-column client-service layout using the same WordPress-owned sources.
- **Compact** — reduced-height Footer for content-heavy or landing-oriented sites.

Preset selection is Theme-owned presentation state in the existing settings schema.

All presets must fail soft when one or more Footer menu locations are empty. Empty columns disappear without leaving broken headings or layout gaps.

### 7.4 Interaction and accessibility

Footer navigation retains semantic `<nav>` landmarks with meaningful labels, keyboard reachability, visible focus, responsive stacking and no horizontal overflow at supported widths.

No JavaScript is required for the core Footer layout.

## 8. Y4 — Professional Services Starter Blueprint

### 8.1 Goal

Reduce the time needed to prepare a new general professional-services/business site while preserving the accepted provisioning architecture.

### 8.2 Reuse, not a second provisioning engine

Y4 extends the existing confirmed, idempotent WordPress-native provisioning workflow. It does not create a parallel installer or onboarding database.

All D-025/D-026 safety rules remain in force:

- Theme activation itself is mutation-free;
- a visible change plan is required before mutation;
- the user explicitly confirms the plan;
- current-run rollback is bounded;
- successful setup does not mean Launch Ready;
- active/existing sites fail safe instead of being overwritten;
- authoritative content/mapping mutations remain explicit in the confirmed plan.

### 8.3 Generic site structure

For a new/mostly-empty site, the blueprint may propose creation or mapping of:

- Home;
- About / Giới thiệu;
- Services / Dịch vụ;
- Team / Expertise / Đội ngũ;
- Contact / Liên hệ;
- Blog / Tin tức presentation target where WordPress configuration requires it;
- primary navigation;
- Footer navigation/policy/contact menu locations where suitable.

The blueprint may also propose an appropriate Theme visual preset, Page presentation and Footer preset.

### 8.4 Content behavior

Created Pages use WordPress-native block content built from the Y2 kits. Created content is immediately WordPress-owned and editable.

The blueprint may seed neutral replaceable copy but may not fabricate client identity, credentials, addresses, contact details, testimonials, service success claims or other authoritative facts.

Existing Pages with exact intended WordPress mapping are proposed for reuse through the existing provisioning discovery/change-plan flow rather than duplicated.

### 8.5 Existing-site safety

On a site that is not clearly new/mostly empty, Y4 must not mass-create or overwrite production content. The plan may recommend mappings and can create bounded Draft content only where the already accepted provisioning policy permits it.

## 9. Y5 — Client Delivery QA & Release Closure

### 9.1 Goal

Prove v1.3 as an end-to-end client-delivery system, not merely as independent components.

### 9.2 Clean-site journey

The release candidate must be tested on the supported WordPress/PHP floor with zero mandatory third-party plugins:

1. clean install;
2. activate Theme;
3. run the professional-services blueprint through the confirmed plan;
4. verify Homepage and all core generated/mapped inner Pages;
5. verify Header + Footer + navigation;
6. edit representative Page content in WordPress and confirm frontend parity;
7. verify update/theme-switch continuity;
8. build the deterministic release package;
9. install/activate the exact package and rerun the client-delivery smoke matrix.

### 9.3 Browser matrix

At minimum, Y5 covers representative Homepage, About, Services, Team/Expertise, Contact, Blog/listing, Post, Search and 404 surfaces across desktop/tablet/mobile widths.

The matrix checks:

- HTTP and WordPress route truth;
- one Theme document-level `<main>`;
- heading/landmark integrity;
- responsive layout and horizontal overflow;
- keyboard/focus behavior;
- blocking axe findings within Theme ownership;
- Theme console/page/request errors;
- surface-aware asset loading;
- Page variant and Footer preset behavior.

### 9.4 Release integrity

Y5 retains the established v1.x release discipline:

- L1 static/source boundary;
- L2 RED -> GREEN contracts for production slices;
- L3 real WordPress runtime;
- L4 browser/visual/a11y;
- L6 deterministic package/source identity, packaged PHP lint, switch-away/switch-back and rollback evidence;
- exact-final-head verification before canonical merge;
- exact-main verification after merge before publication disposition.

Provider L5 is not part of v1.3 Core completion.

## 10. Version discipline

The currently published/production version remains `1.2.0` while Y1-Y4 are developed.

No slice may opportunistically change only one version declaration. Promotion to `1.3.0` is a distinct Y5 gate after fresh final-candidate evidence and explicit product-owner approval, following the existing atomic `style.css` + `AZNET_THEME_VERSION` discipline.

Git tag, GitHub Release publication and production deployment remain separate approval gates after technical integration.

## 11. Files and component boundaries

The implementation plan should prefer the current structure and keep responsibilities narrow. Expected areas include:

- `page.php` and small Page presentation helpers;
- optional native Page Template files for Wide/Landing variants;
- `inc/theme/` modules for Page presentation, settings integration and provisioning extension;
- `patterns/` for curated native Page kits;
- `template-parts/footer/site-footer.php` plus Footer presentation helper(s);
- surface-aware component CSS under `assets/css/components/`;
- existing admin/Control Center schema/UI only where a bounded presentation setting must be exposed;
- dedicated offline/runtime/browser tests and workflow evidence per slice.

Large existing files should not absorb unrelated responsibilities. In particular, the already-large provisioning blueprint module should be split or extended through a focused v1.3 module if adding the professional-services blueprint directly would materially worsen cohesion.

## 12. Failure and fallback behavior

v1.3 must fail soft:

- missing Page excerpt -> omit supporting text;
- missing featured image -> render a complete text-only Page header;
- top-level Page -> no default breadcrumb;
- invalid/missing ancestor -> omit only the invalid breadcrumb item rather than infer a route;
- empty Footer menu location -> omit that Footer region cleanly;
- unsupported/new setting value -> normalize to the default allowed preset;
- provisioning precondition not met -> no unsafe mutation; report the plan as blocked/ineligible;
- optional provider absent/error/version mismatch -> no Core failure and no private fallback read.

No fallback may invent authoritative business data.

## 13. Performance rules

Assets remain surface-aware.

- Page-specific presentation CSS loads only where needed.
- Footer CSS is allowed globally because the Footer is a global site-shell surface, but v1.3 must measure the delta rather than assume it is negligible.
- Pattern editor styles must not force unrelated frontend assets globally.
- No bundler/build stack is introduced unless a separately accepted decision demonstrates a real need.

## 14. Accessibility rules

All new Theme-owned UI must support:

- semantic landmarks;
- valid heading hierarchy under normal authored content;
- visible keyboard focus;
- reasonable link target sizing;
- responsive reflow without horizontal scrolling at the supported widths;
- reduced-motion respect where motion exists;
- sufficient contrast within Theme-controlled colors;
- no inaccessible decorative image alt text generated by the Theme.

The Theme does not claim ownership of accessibility defects authored directly inside client Page content, but its patterns must ship with accessible defaults.

## 15. Explicit non-goals

v1.3 does **not** add:

- a proprietary page builder;
- a block replacement/editor fork;
- arbitrary drag/drop Header/Footer builder;
- mega-menu application logic;
- custom form submission or CRM workflow;
- custom search/filter engine;
- SEO canonical/meta/schema/OG generation;
- business/service/domain data stores;
- RootProfile/ConvertFlow/Woo source code;
- provider L5 certification;
- private-provider detection or storage reads;
- launch-readiness claims based only on provisioning success.

## 16. Acceptance gates by slice

### Y1 exit

- native Page presentation implementation complete;
- backward-compatible WordPress content behavior;
- Page hierarchy breadcrumb rule proven;
- Standard/Wide/Landing variants proven;
- L1-L4 fresh evidence;
- retained core regressions green.

### Y2 exit

- five professional Page kits available as native WordPress content/pattern compositions;
- no fabricated authoritative client facts;
- editor/frontend parity and theme-switch content portability proven;
- responsive/a11y matrix green.

### Y3 exit

- Standard/Professional/Compact Footer presets available through the existing settings store;
- empty-menu fail-soft behavior proven;
- mobile/keyboard/focus/a11y green;
- no new authoritative contact/social store.

### Y4 exit

- professional-services blueprint integrated into the existing confirmed provisioning flow;
- clean/new-site idempotency and current-run rollback proven;
- active-site no-overwrite/fail-safe behavior proven;
- generated content is WordPress-native and editable;
- no invented client truth.

### Y5 exit

- complete clean-site client-delivery journey passes on exact final candidate;
- exact package/source identity and lifecycle continuity pass;
- final package has no mandatory third-party runtime dependency;
- exact-main post-merge verification passes;
- only then may the owner decide on `1.3.0` publication and later production deployment.

## 17. Source/governance implications

This design creates a new Theme roadmap milestone and therefore requires authoritative reconciliation before production implementation:

- AZT-04 must ratify milestone **Y — v1.3 Client Delivery System**, its Y1-Y5 sequence, QA gates and version discipline.
- The derived AZT-EXEC-MAP and SOURCE_MANIFEST must be aligned after ratification.
- AZT-01 ownership does not change: the milestone improves presentation and WordPress-native delivery workflow only.
- AZT-02 public integration contracts do not change.
- AZT-05 release constitution does not change unless later implementation discovers a true constitutional conflict.
